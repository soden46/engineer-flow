# v0.2.0 - Project-Aware Skill Routing

Language: [English](#english) | [Bahasa Indonesia](#bahasa-indonesia)

<a id="english"></a>

## English

Engineer Flow v0.2.0 makes sparse specialist routing project-aware. External Agent Skills can now be discovered from bounded project evidence even when the user task does not name the technology, and explicit skill names compare consistently across `-`, `_`, `:`, and space separators. The 0-2 specialist architecture, persistent memory infrastructure, and mandatory post-development security review are preserved unchanged.

## Highlights

- Project-aware external skill retrieval.
- Framework/language agnostic matching.
- No technology hardcoding and no dependency-to-framework mapping tables.
- Bounded project evidence collection (root manifests only).
- Explicit-name delimiter normalization.
- No fuzzy matching introduced.
- Maximum 0-2 specialists per task remains unchanged.
- Zero false external activation in fresh heldout-v5.
- Existing secure memory and post-development security architecture preserved.

## How Project-Aware Retrieval Works

External specialist relevance now combines four signals:

```text
task
+ task intent
+ bounded project manifest evidence
+ installed external skill identity
```

Before routing, Engineer Flow reads common dependency manifests at the project root (`package.json`, `composer.json`, `pyproject.toml`, `requirements*.txt`, `pom.xml`, Gradle files, `go.mod`, `Cargo.toml`, `pubspec.yaml`, `Gemfile`) under strict bounds: at most 16 files, 64 KB per file, 256 KB total, root-level only.

An installed external skill provides its own identity signal, derived generically from the skill's own name. Generic anchor vocabulary such as `development`, `configuration`, or `database` can never activate a skill on its own.

Conceptually:

```text
project manifest contains dependency evidence
+ installed specialist identity matches that evidence
= specialist becomes relevant
```

For example, when `composer.json` contains `laravel/framework` and a skill named `laravel-development` is installed, that specialist becomes relevant even if the task text never says "Laravel". The same works for any ecosystem whose installed skill carries its identity in its name.

Task intent is derived only from existing internal capability scoring and never decides final primary/support routing directly.

## Explicit Skill Names

These forms are treated equivalently for explicit-name comparison:

```text
example-specialist
example_specialist
example:specialist
example specialist
```

Clarifications:

- exact-name normalization only
- no fuzzy matching, no stemming, no embeddings
- unrelated partial names do not activate specialists; `cache` alone does not match a skill named `cache-query-optimizer`

## Architecture Preserved

- 16 generalized internal capabilities.
- Maximum 2 development specialists.
- External Agent Skills remain dynamically discovered.
- Persistent memory is infrastructure and does not consume a specialist slot.
- Mandatory post-development security remains enabled.
- No bundled framework-specific knowledge is required.

## Known Limitations

- Morphology and singular/plural lexical mismatches can still zero out otherwise relevant matches.
- Skill body text is not currently part of ordinary relevance scoring.
- Broad headings may sometimes over-capture relevance, especially for `security`.
- Support-specialist selection can still vary on ambiguous cross-cutting tasks.

These are planned research areas for a future version and were not silently changed in v0.2.0.

## Cara Kerja Project-Aware Retrieval

Relevansi specialist eksternal sekarang menggabungkan empat sinyal:

```text
task
+ task intent
+ bounded project manifest evidence
+ identitas installed external skill
```

Sebelum routing, Engineer Flow membaca manifest dependency umum di root project (`package.json`, `composer.json`, `pyproject.toml`, `requirements*.txt`, `pom.xml`, file Gradle, `go.mod`, `Cargo.toml`, `pubspec.yaml`, `Gemfile`) dengan batas ketat: maksimum 16 file, 64 KB per file, total 256 KB, hanya root-level.

Installed external skill menyediakan sinyal identitasnya sendiri, yang diturunkan secara generik dari nama skill tersebut. Kosakata anchor generik seperti `development`, `configuration`, atau `database` tidak akan pernah mengaktifkan sebuah skill dengan sendirinya.

Secara konseptual:

```text
manifest project berisi evidence dependency
+ identitas specialist terinstall cocok dengan evidence itu
= specialist menjadi relevan
```

Contohnya, saat `composer.json` berisi `laravel/framework` dan skill bernama `laravel-development` terinstall, specialist itu menjadi relevan meskipun task tidak pernah menulis "Laravel". Mekanisme yang sama berlaku untuk ecosystem apa pun yang skill terinstallnya membawa identitas pada namanya.

Task intent diturunkan hanya dari scoring capability internal yang sudah ada dan tidak pernah memutuskan routing final primary/support secara langsung.

## Nama Skill Eksplisit


- hanya normalisasi exact-name
- tanpa fuzzy matching, tanpa stemming, tanpa embeddings
- nama parsial yang tidak terkait tidak mengaktifkan specialist; `cache` saja tidak mencocokkan skill bernama `cache-query-optimizer`

## Keterbatasan yang Diketahui

- Ketidakcocokan morfologi serta bentuk tunggal/jamak masih bisa membuat pencocokan leksikal relevan menjadi nol.

- Heading yang sangat luas kadang over-capture relevance, terutama untuk `security`.
- Pemilihan support specialist masih bisa bervariasi pada task lintas domain yang ambigu.

Ini adalah area riset yang direncanakan untuk versi berikutnya dan tidak diubah diam-diam pada v0.2.0.
